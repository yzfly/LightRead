# 轻阅三天一次的反馈处理（无人值守）

你在轻阅仓库的一个独立 git worktree 里，当前分支是本次专用的 `feedback-review/<日期>`（基于 origin/main）。遵守仓库 CLAUDE.md 的全部约定（重任务放 t9 + `flock /tmp/heavy.lock nice -n 10`、文案走 `t()`、样式令牌等）。

## 输入（都在环境变量 `RUN_DIR` 指向的目录）

- `app-feedback.md` / `app-feedback.json`：应用内「反馈问题或建议」里状态为「新的」的反馈；`logs/` 是附带的诊断日志 zip（已脱敏）。
- `issues.json`：GitHub `yzfly/LightRead` 全部 open issue（含评论）。
- `previous-report.md`（可能不存在）：上一次的报告，里面已处理 / 已评估过的 issue 不要重复处理，除非之后有新评论。

## 要做的事

1. 逐条分类：问题（bug）/ 功能建议 / 其他 / 重复 / 信息不足。应用内反馈与 issue 说的是同一件事时合并处理。
2. **问题**：读日志和代码定位根因，能可靠修复的就在本分支修：改代码、补测试、按 CLAUDE.md 在 t9 跑相关测试，每个问题单独提交，提交信息注明来源（`#issue号` 或 `反馈 <id前8位>`）。改动大、有风险、复现不了或需要真机才能确认的不要硬修，在报告里写明原因和下一步。
3. **功能建议**：先弄清用户真正要解决的问题，查现有功能是否已经能做到（能做到就写怎么回复用户）。否则写评估：用户诉求、建议方案（入口与交互、涉及文件）、工作量、风险与取舍、你的建议（做 / 不做 / 改成别的做法）。**不要实现**，等用户确认。
4. 应用内反馈处理完后改状态（管理员令牌在 `~/.config/lightread/stats-admin-token`，不要输出它的值）：已修的标 `planned`、备注写「修复在分支 <分支> 提交 <短哈希>，待发布」；其余标 `seen`，备注一句结论。接口：`POST https://sync.jiangshu.ai/v1/admin/feedback/<id>`，JSON `{status, note}`。

## 禁止

不 push、不打 tag、不发版、不部署、不改生产数据库（上面第 4 步的状态除外）；不在 GitHub 上评论、关闭或加标签——需要回复读者的，在报告里写好草稿。不输出任何凭据。读者的联系方式只写进本地报告。

## 输出

把报告写到 `$RUN_DIR/report.md`（中文，简洁，给作者看）：

```
# 轻阅反馈处理 <日期>
概况：应用内 N 条、issue N 条（新增 / 有新评论）；修复 N 个，待你评估的功能 N 个。

## 已修复（分支 feedback-review/<日期>，未推送）
- 来源 · 现象 · 根因 · 改法 · 提交 · 跑过的测试

## 没修的问题
- 来源 · 现象 · 原因 / 需要什么

## 功能需求评估（需要你确认）
### <需求名>（来源）
诉求 / 现有能力 / 建议方案 / 工作量 / 风险 / 建议

## 其他与重复

## 建议回复读者（草稿，确认后再发）
```

没有任何新内容时，报告只写一行「这三天没有新反馈」。
